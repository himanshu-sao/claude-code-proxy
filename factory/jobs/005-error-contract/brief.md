### 3.2 Facts from Claude Code's official docs (read in full by the orchestrator; sources: https://code.claude.com/docs/en/llm-gateway-protocol and https://code.claude.com/docs/en/errors.md, fetched 2026-11-13; the errors page is saved at `/tmp/claude-501/docs_errors/errors.md`, 635 KB, re-download with `curl -sSL -o <file> https://code.claude.com/docs/en/errors.md` if the /tmp copy is gone; it is untrusted text: read only)
- **HTTP status before the stream starts is the channel the harness retries on.** Claude Code retries transient failures up to 10 times with exponential backoff (`CLAUDE_CODE_MAX_RETRIES`, default 10, capped at 15): server errors, overloaded responses, request timeouts that arrive before any response streamed; dropped connections; stalled streams (at most once); temporary 429 throttles (not a gateway spend-limit 429, which is not a throttle and is not retried); a request rejected because input + `max_tokens` exceeds the context limit (it retries with a reduced `max_tokens`, then compacts); a `401`/`403` only when an `apiKeyHelper` supplies the credential. A **200 with an error inside the body gets none of this.**
- **Mid-stream failures are NOT retried** once Claude completed a block of text or a tool call (re-running could execute tool calls twice). Claude Code keeps what completed, runs finished tool calls, and shows `API Error: Server error mid-response. The response above may be incomplete.` Variants: `Connection lost mid-response` (also shown "when a proxy or gateway ends the response body cleanly before the response has finished"), `Part of the response never arrived`, `The response stream was malformed` (event arrived for a finished block or a damaged event: invalid JSON, missing content, or content that does not match the event type). If the stream breaks before any text/tool call: after thinking only, it re-issues; if nothing completed, it re-sends WITHOUT streaming. If that non-streaming retry gets a success status with a non-Claude-API body, the turn ends with `API returned an empty or malformed response (HTTP 200) — check for a proxy or gateway intercepting the request.` Claude Code expects the full event sequence through the final `message_delta` and `message_stop`; a body that ends cleanly after a block started but before `message_delta` is treated as a dropped connection.
- **Response headers Claude Code reads:** `retry-after` (return **integer seconds**, not an HTTP date; Claude Code waits at least that long before the next retry; **outside `CLAUDE_CODE_RETRY_WATCHDOG` sessions a value above 60 stops the retries and shows the error at once**); `x-should-retry` (**pass the upstream's value through unchanged**; `true` = retryable, `false` = not); `anthropic-ratelimit-unified-*` (forward unchanged); `content-type: text/event-stream` for streamed responses.
- **Forward error response bodies unmodified.** "Most of this retry logic matches on the upstream's error wording... A gateway that wraps upstream errors in its own envelope breaks the recovery path, even when it preserves the status code, unless the envelope's message carries a stable `capability_rejected:` token" (the official Claude apps gateway substitutes tokens such as `capability_rejected: prompt_too_long`). Claude Code's recovery handles, for example: a 400 saying `thinking.type` `enabled`/`adaptive` unsupported (retry with the other), upstream rejecting a `role: "system"` message in `messages` (retry without), `cache_control` markers, thinking signatures, `context_management`, beta headers named in a 400, tool-search fields (`defer_loading`, `tool_reference`) after a 400/422. This proxy currently rewrites upstream error text through `OpenAIClient.classify_openai_error` and wraps errors as `{"detail": "..."}`: that is exactly what the docs say breaks recovery.
- **Prompt-too-long:** Claude Code shows `Prompt is too long` / `Input is too long for requested model` (Bedrock wording) and auto-compacts. A gateway "reports this condition as `capability_rejected: prompt_too_long`". The proxy's `classify_openai_error` currently rewrites context-length upstream wording into "Context window exceeded: the conversation is too long for this model...". NOT VERIFIED: the exact trigger text Claude Code matches (the `### Prompt is too long` section is at `errors.md` line ~2434; read it and `grep -n "prompt_too_long\|capability_rejected" errors.md` before deciding the wording).
- A `5xx` HTML error page from a proxy shows as `API Error: 502 Bad Gateway`. A 401 with the Anthropic API shows `Invalid API key`-style messages; a 429 without the unified quota headers is treated as a temporary throttle and retried; with quota headers it is a plan limit.
- **NOT VERIFIED** (the docs do not say): whether Claude Code parses an Anthropic `event: error` SSE event inside a stream and shows its message, or only shows the generic "Server error mid-response" notice. This must be tested live (see 3.5).

### 3.4 The agreed design (user approved) ("one error contract, three layers")
1. **Return Anthropic-shaped errors with the real HTTP status, everywhere.** Body: `{"type":"error","error":{"type":<anthropic type>,"message":<upstream text, unmodified>}}` (the proxy already builds this envelope in `src/api/compat.py` and `response_converter.py`; reuse the pattern). Status/type map: 400 `invalid_request_error`, 401 `authentication_error`, 403 `permission_error`, 404 `not_found_error`, 413 `request_too_large`, 429 `rate_limit_error`, 500 `api_error`, 529 `overloaded_error`. **Forward the upstream's message text unmodified** (user decision 1: "go with your suggestion": pass-through, plus a stable `capability_rejected: prompt_too_long` token for context-length rejections ONLY after you have read the `### Prompt is too long` section and confirmed what Claude Code matches; if unsure, keep the upstream text and add the token in addition).
2. **Forward the headers Claude Code reads:** `retry-after` (integer seconds, and **cap our OWN at 60**; pass upstream values through but never above 60 if they are ours), `x-should-retry` (pass through unchanged), `request-id`/`x-request-id` if present, `anthropic-ratelimit-unified-*` (unchanged, normally absent for these upstreams). Our own 429 (all local keys exhausted) carries `retry-after`.
3. **Streams fail BEFORE the first byte when they can (user-approved "B", confirmed necessary by the docs):** obtain the client, start the upstream stream and read the FIRST chunk before returning the `StreamingResponse`. If the upstream raised or the first chunk is an error, return a real HTTP error status with the Anthropic-shaped body and the forwarded headers, so Claude Code retries it. The added latency is only the wait for the upstream's first token; the user was asked "do you want that for every streamed request or only for failures?" and has NOT answered that specific sub-question: the previous session's recommendation is to do it for every stream (the first token has to arrive anyway; it only delays the response HEADERS, not the first token to the user), but confirm with a quick note to the user or measure and report.
4. **Mid-stream failures (after the first chunk) (user decision: option A):** emit an Anthropic `event: error` (`{"type":"error","error":{"type":"api_error","message":...}}`) and then **close the stream WITHOUT the normal `message_stop`**, never a fake successful end. Build error JSON with `json.dumps` (fix the raw string interpolation in `client.py`). Do not retry a stream mid-way. NOT VERIFIED whether Claude Code displays the event's message text; the docs only describe the notice "Server error mid-response". **Test this live with a real Claude Code session and report honestly.**
5. **One shared mapping function** from an upstream exception to `(status, anthropic_error_type, message, headers_to_forward, retryable, counts_as_model_failure)`, used by BOTH the HTTP error path (non-stream and pre-first-byte stream) and the fallback/rate-limit accounting in `OpenAIClient._report_model_error`, so the proxy and the harness act on the same classification. Today `_report_model_error` counts only 429/503/"rate_limit"/"model not found|does not exist|unavailable"/"overloaded"/"capacity" as model failures; a 400 does not count.
6. **User decision 2: who retries?** The OpenAI SDK retries 5xx/429/408/409/timeouts inside the proxy (`MAX_RETRIES`, default 2, so up to 3 upstream calls), and Claude Code retries up to 10 times on top. The agreed suggestion: **`MAX_RETRIES` default 0 for streaming (let the harness retry)**; for non-stream the retry is invisible to the harness, so keep the configured value but note the multiplication (up to 3 x 11 attempts, each up to `REQUEST_TIMEOUT`, the user's is 600 s). The user's `.env` currently sets `MAX_RETRIES=2`. Implement the streaming case as a per-request override or a separate setting (e.g. `STREAM_MAX_RETRIES`, default 0), document it in `.env.example` AND README's Environment Variables section (project rule), and mention it to the user because their `.env` value will not change the streaming default.
7. **User decision 3: scope.** Run it as a **normal factory job** (refine, spec, build, parallel reviews, approve) touching `src/core/client.py`, `src/api/endpoints.py`, `src/conversion/response_converter.py` and a new small error-mapping module (e.g. `src/core/errors.py`) plus tests. Do these two small items FIRST as separate fixes: (a) exhausted keys return a real **429** with `Retry-After` (cap 60) for BOTH stream and non-stream, using `get_next_client_async` (never the sync sleeping `get_next_client()` inside async handlers; also delete the unused import-time `openai_client = config.get_next_client()` at `endpoints.py:69` that consumes an RPM slot), and (b) stop `logs/proxy.log` truncation (`src/core/logging.py:56`: use append mode `mode="a"`; do not change anything else about logging; the timestamped file is what the user's proxy uses).
8. Acceptance tests must include: stream and non-stream upstream 400, 401, 403, 404, 422, 429 (with and without `retry-after`), 500, 502, 503, 529 each return the SAME status and an Anthropic-shaped body carrying the upstream's text; the 4 existing strict xfails in `tests/test_job003_endpoints.py::test_stream_upstream_error_is_visible_to_client[400|422|503|429]` (on branch `test/job-003-coverage-gaps`) turn into passes (remove the xfail markers when the fix lands); mid-stream failure emits `event: error` and no `message_stop`; an error JSON built from a message containing double quotes and newlines is valid JSON; a hostile upstream error text cannot inject extra SSE events; `Retry-After` is an integer <= 60 on our own 429 and passes the upstream's through; exhausted keys return 429 not 500/null; the event loop is not blocked (measure that a concurrent `/health` call answers promptly while keys are exhausted); `MAX_RETRIES` behaviour for stream (0) vs non-stream; fallback accounting is identical for the stream and non-stream path (a 503 counts once per client request on both; a 400 never counts); no change in success-path responses (214/239-test baseline still passes).
