# Spec 005-error-contract-a: shared error mapping + client refactor

## Goal
Add `src/core/errors.py`, one place that turns an upstream OpenAI-SDK exception into the Anthropic status, error type, message, forwarded headers and accounting decisions. Make `OpenAIClient` use it on both paths. Remove the f-string JSON (raw `error_msg` interpolation) and the bare `data: {"error"...}` stream lines. No edits to `endpoints.py` or `response_converter.py` (slices C and D). Owns G5, G11 and edge cases 1, 8, 11, 13, 14.

## Approach (3 files)
- `src/core/errors.py` (new). Stdlib plus `openai._exceptions` only. It must not import `src.core.config` or `src.core.client`.
  - `class MappedError(NamedTuple)` with fields `status:int, error_type:str, message:str, headers:Dict[str,str], retryable:bool, counts_as_model_failure:bool`. It unpacks as the 6-tuple.
  - `map_upstream_error(exc: BaseException, api_key: Optional[str] = None) -> MappedError`.
    - Status: `exc.status_code` if it is an int, else 500. `AuthenticationError` is 401 and `RateLimitError` is 429 even if `status_code` is missing. A non-`APIError` exception maps to 500 with message `"Unexpected error: " + str(exc)`.
    - Type table: 400 invalid_request_error, 401 authentication_error, 403 permission_error, 404 not_found_error, 413 request_too_large, 429 rate_limit_error, 500 api_error, 529 overloaded_error. Other 4xx map to invalid_request_error and other 5xx to api_error, with the status kept.
    - Message is the upstream text, unmodified. Take `body["error"]["message"]` (or `body["message"]`) if `exc.body` is a dict and that value is a non-empty str. Otherwise take `exc.message`, then `str(exc)`. If the result is empty or whitespace (edge 1), use `f"Upstream error (HTTP {status})"`.
    - Redaction (edge 14): if `api_key` is a non-empty string, replace every occurrence in the message with `[redacted]`.
    - Prompt-too-long (edge 13): when the status is 400 or 413 and the lowercased `message + str(exc)` contains any of `context_length_exceeded`, `maximum context length`, `string too long`, `context window` or `too many tokens` (the exact triggers of today's `classify_openai_error`, which is deleted), or `exc.code == "context_length_exceeded"`, the message becomes `"capability_rejected: prompt_too_long " + message`. Other statuses and other 400s are never prefixed.
    - Headers come from `exc.response.headers` when `exc.response` exists, matched case-insensitively and emitted lowercase. Forward `retry-after` only if it matches `^\d+$` (an HTTP-date or non-integer is dropped). Forward `x-should-retry`, `request-id` and `x-request-id` unchanged, plus any `anthropic-ratelimit-unified-*`.
    - `retryable`: the upstream `x-should-retry` ("true" or "false") wins if present. Otherwise it is `status in (408, 409, 429) or status >= 500`.
    - `counts_as_model_failure(status, str(exc))`, the current `_report_model_error` rule moved here unchanged: status 429 or 503; or text (lowercased) containing `rate_limit`, `overloaded` or `capacity`; or `model` together with `not found`, `does not exist` or `unavailable`. A 400 does not count unless its text matches.
  - `counts_as_model_failure(status: int, text: str) -> bool`, a public helper used by the above and by the client.
  - `error_envelope(error_type: str, message: str) -> dict` returns `{"type":"error","error":{"type":...,"message":...}}`. `error_json(error_type, message) -> str` is `json.dumps(envelope, ensure_ascii=False)`. It is the only way error JSON is built.
  - `class UpstreamError(Exception)` carries `.mapped: MappedError` and `str()` is the message. `class UpstreamHTTPError(UpstreamError, HTTPException)` sets `status_code=mapped.status`, `detail=mapped.message` and `headers=mapped.headers or None`.
- `src/core/client.py`:
  - Add private `_handle_upstream_exception(exc) -> MappedError`. It calls `map_upstream_error(exc, self.api_key)`, logs and calls `config.report_model_failure(...)` once if `counts_as_model_failure` (via `_report_model_error`), and calls `config.report_rate_limit(self.api_key)` for `RateLimitError` as today.
  - `create_chat_completion` keeps the 499 `HTTPException` for cancellation. Every other failure raises `UpstreamHTTPError`. Because it is an `HTTPException` subclass, the unchanged endpoint re-raises it and FastAPI answers `{"detail": <message>}` with the real status and forwarded headers. `tests/test_client_retries.py` and the non-stream `detail == message` checks in `tests/test_job003_endpoints.py` stay green unmodified.
  - `create_chat_completion_stream` no longer yields error lines. It raises plain `UpstreamError`, deliberately not an `HTTPException`. The current converter re-raises `HTTPException`, which would crash the response after headers are sent. It catches `Exception`, emits one `event: error` (message text not exposed yet) and ends with no `message_stop`. Stream tests expecting HTTP 200 stay green, and the 4 strict xfails in `test_job003_endpoints.py` stay xfailed (the upstream text is not in the body until slice D). On cancellation it reports 499 via `_report_model_error` and returns without yielding.
  - `_report_model_error(status_code, error_detail)` keeps its signature but delegates the decision to `errors.counts_as_model_failure`. Delete `classify_openai_error` (no tests or src callers remain) and the f-string JSON.
- `tests/test_errors.py` (new, offline). Build SDK errors as `_api_error` does in `test_job003_endpoints.py`, using `httpx.Response(status, headers=..., request=...)`.

## Acceptance criteria
1. Mapping table: for each of 400, 401, 403, 404, 413, 422, 429, 500, 502, 503, 529, `map_upstream_error` returns the status and type from the table with `message` equal to the upstream text. A body-less or empty-message error gives the `Upstream error (HTTP n)` fallback (edge 1). Forwarded headers: integer `retry-after` is kept (including 120); an HTTP-date or `abc` value is dropped; `x-should-retry`, `x-request-id` and `anthropic-ratelimit-unified-*` pass through; unrelated headers are dropped. A 401 whose text contains the client key returns a message without the key (edge 14).
2. Prompt-too-long (edge 13): a 400 whose text contains each of the five triggers (and one with `code="context_length_exceeded"`) gets the exact prefix `capability_rejected: prompt_too_long ` followed by the unmodified text. A plain 400 ("bad request"), a 503 and a 401 containing "context window" get no prefix.
3. G5: `json.loads(error_json("api_error", 'say "hi"\nline2\\'))` round-trips to the same message. `client.py` contains no f-string-built JSON (`grep -n "data: {{" src/core/client.py` returns nothing).
4. G11 and edge 11, driven through a real `OpenAIClient` with `.chat.completions.create` patched to raise (as in `failing_upstream`), on non-stream and stream, with `config.report_model_failure` patched: a 503 reports once per client call, and a 400 and a 401 report zero times. With a real `Config` (`BIG_MODEL="a,b"`, threshold 3), three 503s switch the active model to `b` and a fourth is reported against `b`. `counts_as_model_failure` is True for 429/503 and for the rate_limit/overloaded/capacity/model-not-found texts, and False for a plain 400.
5. Client exposure and Azure (edge 8): non-stream raises `UpstreamHTTPError` (an `HTTPException`) whose `status_code`, `detail` and `headers` match the mapping, and the stream generator raises `UpstreamError` (not an `HTTPException`) with `.mapped` set. `OpenAIClient("k", "https://x.invalid", api_version="2024-02-01")` yields identical mapped results. `python -c "import src.core.errors"` works with no env vars set (no config import).
