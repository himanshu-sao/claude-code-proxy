VERDICT: CHANGES

Scope: `src/core/signal_log.py`, `scripts/analyze_signal_log.py`, `tests/test_signal_log.py` (diff 1d5a0e4..HEAD). I probed the builder with hostile inputs from `$TMPDIR` using the worktree's `src` and a monkeypatched `_log_path`. The real `logs/` was not touched. No new dependencies. No eval, pickle, shell or subprocess in the module or script. The test file uses `subprocess` with `sys.executable` only.

## What holds (verified by probe)
- **Value leaks:** I found none. Header values, system and user text, tool schemas, tool_result text, base64, metadata values and extra-field values never reach the line. An attacker-supplied `output_config.effort`, `thinking.type` or `x-claude-code-request-class` value collapses to `"other"` (signal_log.py:89-94). Exceptions are logged by `type(exc).__name__` only (:233, :362). The `handleError` override (:322) keeps the traceback and the record off stderr.
- **Injection:** `json.dumps(..., ensure_ascii=True)` (:356) escapes `\n`, `\r`, ESC, U+2028 and RLO. A hostile key such as `AUTOSIGNAL {"a":1}\r\n2024 | fake` stays inside a JSON string, so the output is one physical line. The real `AUTOSIGNAL ` prefix always comes first, so the analyzer's `line.find` (analyze:35) cannot be tricked into parsing a fake record. `logger.info(line)` is called without args, so a `%` in the message is not interpreted.
- **Resource use:** The regex `<system-reminder>.*?(?:</system-reminder>|\Z)` is linear. 300k unclosed or alternating opening tags took about 0.05 s, and a 5 MB prompt took 2 ms. 20k tools took 0.03 s. 200k extra body fields took 0.05 s. Tool_use input nested 900 deep and tool_result nested 3000 deep both raise RecursionError. Each section catches it, so the builder returns a record without `est_tokens` and never raises.
- **Thread safety:** The double-checked handler creation under `_lock` is correct. The stdlib handler serialises writes with its own lock.

## Findings (fix before PASS)
1. **"Content-free" holds for values but not for names (signal_log.py:244-246, :273, :303, `_names` at :85-86).** `body_fields`, `header_names`, `oc_keys`, `meta_keys` and `model` are client-controlled free text. They are logged raw, capped at 64 chars and 50 entries per list. My probe put a marker string in `model` and it came out verbatim. Real Claude Code traffic will not do this, but the spec and the user require strictly content-free output, and these are the only channels left. Fix: pass every name through a pattern filter in `_cap` and `_names`, e.g. `re.fullmatch(r"[A-Za-z0-9_.:/\-]{1,64}", s)` or else the literal `"other"`. Apply the same filter to `model`, and keep the list cap. Add a test with a prose-like key or a `model` containing spaces, and assert the line contains neither.
2. **File permissions (signal_log.py:335-342).** The log is created as 0644 in a 0755 directory, because it follows the umask. It persistently holds unsalted prompt hashes and session-id hashes, so other local users can read it. Fix: override `_open` in `_SignalFileHandler` to create the file with `os.open(..., O_WRONLY|O_APPEND|O_CREAT, 0o600)` and then `os.chmod(path, 0o600)`. Rotated files are renamed from it, so they keep the mode. Optionally add `O_NOFOLLOW`: with a symlink at `logs/auto_signal.log` the current code follows it and appends to the target (probed). That is operator-owned, so it is low risk, but the flag costs nothing.
3. **Env limits are unbounded (signal_log.py:55-60, :338-339).** `AUTO_SIGNAL_LOG_BACKUP_COUNT=5000000` made each rollover loop millions of `os.path.exists` calls. In my probe, 3 rollovers took 28 s. `emit_signal` is called synchronously from the async handler, so the event loop would stall for that time. A huge `MAX_BYTES` removes the growth bound the spec promises. Fix: clamp, e.g. `backupCount = min(v, 20)` and `maxBytes = min(v, 1 << 30)`. Add a test.
4. **Big-int field silently drops the record (signal_log.py:250-252, :285-287, :356).** pydantic accepts `max_tokens=10**5000`. `json.dumps` then raises ValueError (the int-to-str digit limit on Python 3.11+), and `emit_signal` swallows it. The result is no line at all, and a client can suppress its own logging. My probe confirmed this: no file was created. Fix: emit `max_tokens` and `think_budget` only when `0 <= v < 2**53`, otherwise None.
5. **Analyzer terminal injection and a crash (analyze_signal_log.py:87-92, :184, :212).** `freq_section` prints names decoded from the log raw, including ESC (`\x1b[31m` came through my probe). A crafted log line with a non-str `sid_hash` or `fm_hash` (a list, say) raises an unhashable-type TypeError at `set.add` and dies with a traceback. Fix: print names with `ascii()` or strip control chars, and require `isinstance(x, str)` for both hashes when building `both`. Low severity because the log is local.

## Hash recommendation (Q2)
- **`sid_hash`: accept as is.** Session ids are random UUIDs (122 bits), so an 8-hex unsalted hash cannot be inverted or guessed. It can only be matched against an id you already hold.
- **`fm_hash`: keep 8 hex, unsalted, for this capture.** This is conditional on fix 2, the 0600 mode.
  - *Dictionary risk:* short or templated first prompts ("hi", "/init", "continue", a slash command) can be confirmed by hashing a guess. That is confirmation, not recovery. The first 512 chars are hashed, so any real prompt is not guessable, and only an attacker who can already read a local gitignored 0600 file benefits.
  - *Collisions:* 32 bits gives about 1% collision probability at 10k distinct values and about 17% at 40k. With the default 5 MB x 4 files and lines of about 600 bytes, retention is about 35k lines, so expected colliding pairs are well below 1. That does not distort the analyzer's (a) or (b) percentages.
  - *Salting:* a salt would break comparison across restarts and rotated files, which is the reason to keep unsalted. If the operator wants more protection, add an optional `AUTO_SIGNAL_LOG_SALT` env var that switches to HMAC-SHA256. It is not needed for PASS.
  - *Job 004:* this verdict does not carry over. A real conversation key needs at least 64 bits, and it should be kept in memory rather than written to a persistent file.
- **Wiring note for T5:** call `emit_signal` after request validation. Offload the file write if possible, because it is blocking I/O on the event loop.
