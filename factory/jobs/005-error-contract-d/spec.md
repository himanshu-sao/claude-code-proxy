# Spec 005-error-contract-d: mid-stream error event

## Goal
After the first chunk, a failing upstream stream must end with exactly one Anthropic `event: error` block (type from the shared mapping, upstream text JSON-encoded) and nothing after it. The success path stays byte-identical. G3 (xfail removal) was done by slice C; this slice owns G4, G6, G12 and edge cases 6 and 7.

## Approach (3 files)
1. `src/conversion/response_converter.py`, only `convert_openai_streaming_to_claude_with_cancellation`. Import `UpstreamError`, `error_json` from `src.core.errors`. Handler order in the `try`:
   - `except UpstreamError as e` FIRST (`UpstreamHTTPError` is also an `HTTPException`, so it must precede that handler). Log `logger.error("Mid-stream upstream error: status=%s type=%s", e.mapped.status, e.mapped.error_type)` (no message text, no traceback). Yield `f"event: error\ndata: {error_json(e.mapped.error_type, e.mapped.message)}\n\n"`, then `return`.
   - `except HTTPException` with 499: unchanged (existing `cancelled` event); other statuses re-raise, unchanged.
   - `except Exception as e`: keep the log lines, but the event becomes `error_json("api_error", f"Streaming error: {type(e).__name__}")`. Never put `str(e)` or `safe_error_summary(e)` in the client payload. Then `return`.

## Exact behaviour
- Error block bytes: `event: error\ndata: {"type": "error", "error": {"type": "<error_type>", "message": "<text>"}}\n\n` (`json.dumps` default separators, `ensure_ascii=False`, as `error_json` produces). Newlines/quotes in upstream text become `\n`/`\"` inside the JSON string, so a text like `"x\n\nevent: message_stop"` yields exactly one line starting with `event:` after the error begins and no `message_stop` anywhere.
- Ending (edge case 6, decision): after the error block emit NOTHING: no `content_block_stop` for the open text block (index 0) or any started tool block, no `message_delta`, no `message_stop`. Reason: Anthropic's documented error signal is `event: error`; Claude Code treats a body that ends after a block started but before `message_delta` as a dropped connection only when no error event arrived, and an error event is terminal. Closing a half-streamed tool_use block would present truncated tool input as a complete block. So the error event is the last bytes of the body.
- Edge case 7 (`[DONE]` with no finish reason): today the loop `break`s on `[DONE]`, then emits `content_block_stop` for index 0 and started tools, `message_delta` with `stop_reason: end_turn` and the last-seen usage, then `message_stop`. Keep that (a clean ending is what a lenient upstream expects; no error). Pin it with a test. Same for a stream that just ends without `[DONE]`.

## Acceptance criteria
1. (G4) Stub stream yields one text chunk, then raises `UpstreamError(map_upstream_error(...))` for 503 / 429 / 400 in turn. The output ends with one `event: error` block whose JSON equals `{"type":"error","error":{"type":<mapped type>,"message":<mapped message>}}`; the output contains no `message_delta` and no `message_stop`. A non-`UpstreamError` (`RuntimeError("secret sk-abc")`) gives `api_error` with message exactly `Streaming error: RuntimeError` and the text `secret` absent. A 499 `HTTPException` still gives the `cancelled` event.
2. (G6) Upstream text `'x"\r\n\nevent: message_stop\ndata: {}'` yields exactly one line beginning `event: error` and no line `event: message_stop` anywhere; `json.loads` of the data line returns the original text.
3. (Edge 6) Stream starts a tool call (id+name, partial args), then raises `UpstreamError`: output has a `content_block_start` for the tool index, the error block is the final block, and no `content_block_stop`, `message_delta` or `message_stop` follows it. The test docstring records the decision above.
4. (Edge 7) `[DONE]` as the first data line after a text delta with no `finish_reason`: output ends `content_block_stop`, `message_delta` (`stop_reason: end_turn`), `message_stop`; no `event: error`.
